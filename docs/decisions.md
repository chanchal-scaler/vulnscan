# Decisions

Why vulnscan is built the way it is, including what was tried and rejected. Newest context first within each section. Dates are when the decision was made. Read the relevant entry before changing any of these things.

## Background

The project started (2026-11-03) after two incidents:
1. **An SSRF in a third-party app's URL preview leaked AWS keys.** The attacker granted themselves admin and dumped all of Parameter Store, and rotating every credential took a long time.
2. **Some systems were exploitable through a widely reported vulnerability** (HttpToShell), and the team learned about it from articles, not alerts.

The owner asked for a tool that, given any GitHub repo in their orgs, picks and installs the right scanners, finds the important vulnerabilities, stores results on the machine, and uses a Claude Code token for the LLM part.

The owner's choices:
- a proof of concept;
- only the org's own repos;
- a CLI;
- the language with the best security tooling that's easy to extend;
- a Claude Code subscription token for now.

Many of the infrastructure choices below come from incident 1: limit what a compromised scanner could reach.

## Application

| Decision | Why | Rejected |
|---|---|---|
| **Python, standard library only** (2026-11-03) | Most security tooling is Python or callable from it, and with no dependencies there's no supply-chain surface in the CLI itself. Python 3.9 is still supported for older hosts. | Go: fewer integrations and slower to extend. Third-party frameworks such as click: unnecessary. |
| **Use existing scanners and normalise their output**: semgrep, osv-scanner, gitleaks, checkov, brakeman, bandit, gosec (2026-11-03) | Each is the standard tool for its area. Together they cover code, dependencies, secrets and infrastructure for the org's stacks (Rails, JS, Python, Go, Terraform). | Writing our own rules. Commercial SaaS: code would leave the account. |
| **Never install or run the scanned repo's dependencies** (2026-11-03) | `bundle install`/`npm install` run arbitrary code from the repo. All scanners used work from source and lockfiles. | Running tests or builds, which some deeper analysers need. |
| **Claude through the headless `claude -p` CLI, restricted and read-only** (2026-11-03) | The owner chose a Claude Code subscription token. The CLI's `--restricted`, `--tools Read,Grep,Glob`, `--strict-mcp-config` and a working directory outside the repo give read-only access that can't load the repo's own settings or hooks. `--json-schema` gives structured output. | The Agent SDK or API with an API key: not the owner's choice for now. Bedrock is the planned move ([status.md](status.md)) and needs no code change. |
| **Group, prioritise and batch findings for Claude** (2026-11-04) | On a 7,700-finding monolith, the old "first 150 by severity" sent 141 dependency CVEs to Claude. CVSS rates them high, and `Gemfile.lock`/`yarn.lock` sort before `app/`. Committed private keys, SQL injection, `eval` on params and similar were all flagged by scanners but never reviewed. Now dependencies collapse per package version, noisy rules collapse to 5 samples, secrets and code come first, and up to 400 items are reviewed in batches of 100. On real data, everything on that list moved into batches 1–2. | Raising the 150 limit: one call can't take thousands of findings. Grouping brakeman: its warnings are location-specific (the SQL injection lines), so they're never grouped. |
| **Only batch 1 does the open-ended code review** (2026-11-04) | Repeating it per batch costs time and quota and finds the same things. Later batches only give verdicts. | A separate deep-review mode is planned instead ([status.md](status.md)). |
| **Dependencies grouped by package and version, not by lockfile** (2026-11-04) | One repo had 50 lockfiles. Merging cut critical/high dependency items from 312 to 237. | Keeping the lockfile in the key. |
| **`report.csv`, with formula-injection escaping** (2026-11-04) | Requested for spreadsheets. Findings quote repo content, which is untrusted, so cells starting `=+-@` are prefixed with `'`. | — |
| **Per-org tokens (`GITHUB_TOKEN_<ORG>`) supported, but production uses one classic PAT** (2026-11-04) | A fine-grained PAT can reach only one resource owner, so two orgs need two tokens; the code supports that. The owner chose a single classic PAT with `repo` scope, accepting that it also grants **write** access to every repo the user can reach. | Fine-grained per-org tokens (more secure; easy to switch back to). A GitHub App (best long-term option; needs code to mint installation tokens). |
| **Shallow clone of one branch** (2026-11-03, re-tested 2026-11-04) | Fastest and smallest. Measured on discourse/discourse (27k files): 18 s. **Rejected after testing:** a blobless clone (`--filter=blob:none`) followed by `git checkout` with exclusions fetches **one file per request** (31 requests for 28 files in 30 s), so it would take hours. A blobless clone with sparse checkout batches correctly (1 request), but was no faster on that repo, and it leaves skip-worktree entries that `git ls-files` (and so semgrep) still lists. Skipping images on the biggest repo would save about 580 MB, but clone time there is about 3.5 minutes, which is acceptable. | Full clones (history isn't scanned anyway). Mirror caching between scans: possible later for nightly runs. |
| **Per-scanner timeout of 30 minutes, adjustable per run** (2026-11-04) | One slow scanner shouldn't stall a scan forever, but large repos need longer for semgrep. `VULNSCAN_TOOL_TIMEOUT` and `VULNSCAN_TRIAGE_TIMEOUT` are passed through the wrapper. | — |
| **Validation stage uses Strix** (2026-11-04) | The owner chose agentic PoC validation for stage 2. Strix is headless-first (`strix -n` with CI exit codes), Apache-2.0, seeds findings via `--instruction-file`/`--workspace-file`, caps cost with `--max-budget`, and only reports a finding with a working proof-of-concept — exactly a validation stage. | CyberStrike: TUI/interactive-first, AGPL-3.0, thinner headless story for a pipeline. Building our own agent harness: the scanners-plus-triage approach was already ours; validation needs offensive tooling we'd otherwise write. |
| **GLM 5.3 via OpenRouter for Strix** (2026-11-04) | The owner's choice, and one of Strix's two recommended setups. GLM needs no provider safety-program enrollment (unlike OpenAI/Anthropic/Google models, which need Daybreak/CVP/Fairwind even through OpenRouter), and one OpenRouter key covers the model. `STRIX_LLM`/`LLM_API_KEY` stay standard Strix variables so any LiteLLM model id can replace it. | A Claude API key: stage 1 already uses the subscription token, and the point of stage 2 is a second, independent opinion. |
| **`vulnscan validate` as a separate stage reading stage-1's `report.json`** (2026-11-04) | Stages stay explicit and separately runnable (and re-runnable against the same run folder), the expensive validation is opt-in, and the stage-1 report is a natural handoff: its open findings — confirmed, needs review, not triaged, plus Claude's own — are the validation worklist. `--max-validate` caps it, mirroring `--max-triage`. | Folding validation into `vulnscan scan --validate`: couples two expensive stages and forces the clone to be kept. |
| **vulnscan clones, Strix gets a local directory; the GitHub token never reaches Strix** (2026-11-04) | Strix can take a GitHub URL itself, but that would mean handing it the token (in its environment or its sandbox). Cloning ourselves reuses stage-1's token handling and org allowlist. Strix mounts local targets **writable**, so local folders are copied to a throwaway directory first; our clones are already throwaway. | Passing the repo URL plus `GITHUB_TOKEN`. Pointing Strix at a permanent local checkout (it edits what it mounts). |
| **Strix's Docker sandbox is the boundary where scanned code runs** (2026-11-04) | Stage 2's whole purpose is to run and probe the app, which stage 1 forbids for scanners. Strix's sandbox (`ghcr.io/usestrix/strix-sandbox`, pinned by them) is the isolation boundary; it never runs in the vulnscan container. Only `--url` targets extend reach beyond it, and those are the operator's authorisation to give. | Relaxing the stage-1 invariant inside the vulnscan container. |
| **`vulnscan fix`: one draft PR per Strix-validated finding** (2026-11-04) | The owner's choices. Only `V…` findings are fixed, because they have a working PoC. Stage-1 "confirmed" findings don't. One PR per finding keeps each change small and separately mergeable or revertable. PRs are drafts because Claude can't run the repo's code or tests; that would break the "never run scanned code" invariant. | Fixing stage-1 confirmed critical/high findings too. One PR with all fixes, which is harder to review and merge piece by piece. Ready-for-review PRs. |
| **Fix stage: Claude gets Edit/Write, and vulnscan does the git and GitHub work** (2026-11-04) | The owner's choice, and the one exception to "Claude is read-only". Claude stays `--restricted`, with no shell, web or MCP and no GitHub token. Verified: `--restricted` with `acceptEdits` edits files in `--add-dir` headlessly, but refuses writes to `.git/hooks`. The token stays in vulnscan, which commits, pushes (`GIT_CONFIG_*`) and calls the API. Git hooks never run (`core.hooksPath=/dev/null`), because an operator's global pre-commit hook would read config from the repo. The remaining risk is that repo content steers the change Claude writes; draft PRs plus human review are the control. | Claude read-only, returning patches as JSON for vulnscan to apply: keeps the invariant, but means more code, and multi-step edits fail more often. Giving Claude `gh` or the token: lets repo content reach a credential. |
| **Fix stage refuses public repos** (2026-11-04) | A pushed branch or PR on a public repo discloses the vulnerability before the fix is merged. `--dry-run` works on public repos (patches only), which is also how the stage is tested on OWASP apps. | Opening PRs anywhere the token can push. |
| **PRs include reproduction steps written by Claude, not Strix's raw PoC** (2026-11-04) | The owner asked for steps to reproduce: a `curl` command for HTTP-reachable issues, numbered steps otherwise. This replaces the first version's "no PoC in the PR". Reviewers need the steps to confirm both the issue and the fix, and the repos are private. Claude writes them from the validated PoC and the code, against `$BASE_URL`, with placeholders for credentials and IDs, and with no hostnames or secret values. They end with the behaviour before and after the fix. Strix's raw PoC stays in `validation.md`, because it can contain operator-supplied credentials (`--instruction`), live `--url` targets, or tokens minted during testing. Tested with real Claude: a SQL injection gave a `curl` command, and a committed secret gave numbered steps. The first try printed a shortened form of the secret, so the prompt now forbids partial values too. | Copying Strix's PoC verbatim: it's validated, but its format varies and it may hold credentials. Keeping all exploit steps out of the PR, as the first version did. |
| **The fix prompt puts "don't break the app" on a par with "fix it", and breaking fixes are declared** (2026-11-04) | In the first real run, many PRs were correct as security changes but unsafe to merge. They removed hardcoded defaults or committed key files that deployments may still rely on. One swapped a key file for a mechanism the deployment didn't have, one deleted an endpoint whose callers were unknown, and one assumed which key signs another system's tokens. For a leaked secret, the code change also didn't fix anything: the secret is still in git history, so rotation is the fix. The prompt now has Claude read the deployment config first, prefer backwards-compatible changes, and make no change that rests on an unverifiable assumption about another system. Claude returns `breaking` and `before_merging`, which become a `[breaking]` title tag and a checklist at the top of the PR. Re-tested with real Claude: a committed secret became "read from the environment, keep the current value as the fallback" (not breaking), with rotation in the checklist, and a SQL injection fix kept the existing behaviour. | Not opening a PR for breaking fixes: the fix is often right once callers are confirmed, and hiding it loses that. Skipping secret findings entirely: they still benefit from a checklist and a safe first step. |
| **Fix stage is idempotent per run, by branch name** (2026-11-04) | `vulnscan/fix-<run>-<V id>` is unique per validation run. If that branch already exists on GitHub, the finding is skipped before Claude runs, so a re-run spends no quota on it and opens no duplicate PR. | Looking up open PRs through the API: more calls for the same result. |
| **A read-only dashboard served by vulnscan itself, built from the run folders on every request** (2026-11-04) | The owner wanted to track which findings were discovered, which were validated and which were submitted for fix. The three JSON files already hold all of it, so there's no database and no LLM call. It's stdlib only, like the rest. The page shows PR links, not live PR state: live state would mean giving a long-running server the PAT, which can write to every org repo. Strix's PoCs stay out, for the same reason they stay out of PRs. | A static HTML file copied off the instance (no live view). A page that calls GitHub for PR state. |
| **`fix.json` keeps earlier fix runs' results** (2026-11-04) | For tracking. Before this, every fix run rewrote `fix.json` with only what it handled, so `--only` or a re-run, which marks finished findings `skipped`, lost earlier PR links. Results now merge by `V…` id. A later `skipped` never replaces an earlier result. An earlier result is dropped once its ID names a different finding after a re-validation. | A separate append-only history file (a second format to read). |
| **No re-validation once fix branches exist** (2026-11-05) | A re-validation writes new `V001…` ids, but `vulnscan fix` names branches `vulnscan/fix-<run>-<V id>`. After a re-validation, `fix` skipped a different finding whose id happened to have a branch, and PRs lost their link to the validation. `validate` now checks GitHub with `git ls-remote` and refuses if this run has fix branches. Re-validating before any PR, or after dry runs, still works. To check fixes you need a new scan of the fixed code anyway. | Keeping a history of validations per scan, with the validation time in branch names: much more code, and re-validating would open a second PR for a finding already fixed. Matching new Strix findings to old ids: Strix's wording changes between runs. |
| **Claude's own findings sorted before any report is written** (2026-11-05) | `report.md` numbered them `C01…` after sorting by severity, while `report.json`, `report.csv`, `validate.py` (whose ids Strix names) and the dashboard used list order. So C02 could mean different findings. Sorting the list once makes every place agree, and C01 is the worst. Reports written before this keep their old `report.md` labels. | Numbering `report.md` in list order (ids would be out of order there). |
| **Production wiring for validation deferred** (2026-11-04) | Local-first keeps this change reviewable: the CLI, reports and docs work now. Production needs a pinned Strix install (Docker or host), `/vulnscan/openrouter-token` in Parameter Store, and wrapper changes — infrastructure changes that need the owner's approval anyway. | Wiring the instance in the same change. |

## Deployment

| Decision | Why | Rejected |
|---|---|---|
| **One standalone EC2 instance, managed by Terraform; standalone state** (2026-11-03) | The owner chose standalone EC2, with results stored on the instance. Terraform makes the IAM and network boundary reviewable and repeatable. | ECS/Fargate or CodeBuild: considered but not pursued, per the owner's choice. Joining an existing Terraform repo: the owner chose standalone. |
| **Docker: a pinned image, and a fresh container per scan** (2026-11-03) | Bakes in every runtime (Python, Ruby, Go, Claude CLI), which also fixed gosec failing without Go. Every scanner is pinned with SHA-256 checksums for supply-chain control, and a scanner exploited by a malicious repo lands in a throwaway container. | Installing scanners on the host at scan time (unpinned, and not isolated). |
| **Debian trixie base** (2026-11-03) | Brakeman 8.1 needs Ruby 3.2 or newer; bookworm only has 3.1. | Bookworm with Ruby built separately. |
| **apt over HTTPS** (2026-11-04) | The first build on the instance failed because Debian's mirrors default to plain HTTP and the security group only allows 443. Switched the sources to `https://deb.debian.org`, keeping outbound 443-only. | Opening port 80. |
| **The image is built on the instance from GitHub** (2026-11-03) | Simplest option: no registry and no CI. `vulnscan-build` clones `main` and builds. | ECR plus CI: worth it once there's CI. |
| **Network: own subnet in an existing empty VPC, public IP, no NAT** (2026-11-03/04) | Cost: no $33/month NAT gateway; the public IPv4 address costs $3.65. The security group has no inbound rules, so the IP accepts nothing. The account was at its VPC and internet-gateway limit, so it reuses an existing VPC that's empty and owned by an abandoned stack (details in `ENVIRONMENT.local.md`). It adds its own subnet and route table and modifies nothing the stack owns. | A dedicated VPC (blocked by quota). An IPv6-only setup: github.com has no IPv6. Sharing the main staging VPC: a compromised scanner would share a network with 47 staging hosts. |
| **IAM: a minimal custom policy, not `AmazonSSMManagedInstanceCore`** (2026-11-03) | The managed policy allows `ssm:GetParameter(s)` on `*`, so any instance with it can read every parameter in the account: exactly the dump from incident 1. The custom policy is AWS's minimal Session Manager policy plus `GetParameter` on `/vulnscan/*`. Verified on the instance: reading other parameters gets AccessDenied. | The managed policy. |
| **IMDSv2 with hop limit 1; tokens fetched on the host** (2026-11-03) | Containers can't reach the instance role. The wrapper fetches the two tokens and passes them in by name. | Containers fetching their own tokens (would need hop limit 2 and would give scanners AWS credentials). |
| **Tokens in Parameter Store, created by Terraform as placeholders through write-only `value_wo`** (2026-11-04) | The owner wanted Terraform to create them. With a plain `value`, every plan reads the parameter back, and the provider stores SecureString values **in plaintext in state**. `value_wo` is never stored; checked in the provider source, which sets `value` to null. The owner replaces the placeholder by hand. | Plain `value` with `ignore_changes` (still stored in state). Creating the parameters outside Terraform. |
| **The vulnscan repo is public, so `source-token` is optional** (2026-11-04) | Public repos clone without a token, and `vulnscan-build` uses `source-token` only if it exists. | — |
| **No SSH; Session Manager only** (2026-11-03) | No inbound ports and no keys to manage. Files are copied off by base64 over a non-interactive session ([operations.md](operations.md)). | An SSH key, or SCP over Session Manager (needs SSH keys). |
| **Connect with `AWS-StartInteractiveCommand` running `sudo -i`** (2026-11-04) | The account's Session Manager preferences include a shell profile for the Rails app servers (`cd /var/app/current … rails c`), which spews errors here. Sessions that run a command skip that profile. | Changing the account-wide preference (shared; would affect other teams). |
| **Scans run in detached containers** (2026-11-04) | The account caps sessions at 60 minutes. A foreground `docker run` died with the session, losing a 30-minute scan. Now the wrapper streams `docker logs -f`; the scan survives the session ending and Ctrl-C. | `nohup`/`systemd-run`: requires users to remember them. |
| **Spot, persistent, stop on interruption** (2026-11-04) | About 55% cheaper (about $29/month instead of $55). Interruptions stop the instance, keeping both disks, and it restarts when capacity returns. A scan running at that moment has to be re-run. | On-demand. Spot that terminates on interruption (loses the root disk and image). |
| **t3.large, not t4g.large** (2026-11-04) | t4g.large Spot in us-west-2a failed with `InsufficientInstanceCapacity`, scoring 1 of 10 in every zone. t3.large scored 3 in us-west-2a and has <5% monthly interruptions (t4g: 15–20%). The image builds for both architectures. Note: the variable's default is still `t4g.large`; `terraform.tfvars` sets `t3.large`. | m8g.large in us-west-2d (cheaper and rarely interrupted, but would mean moving the subnet and reports volume to another zone). |
| **Unlimited CPU credits** (2026-11-04) | T3/T4g instances get **no launch credits**. In `standard` mode the image build used up the few earned credits, then the instance ran at its 30% baseline, with 61% steal time while semgrep crawled. Unlimited bills $0.05 per vCPU-hour only if the 24-hour average stays above 30%, which occasional scans don't reach. | `standard` (the original choice, made to avoid surprise charges). |
| **Validate containers get the host Docker socket; scans never do** (2026-11-04) | Strix's pentest sandbox containers must run as siblings on the host daemon — that is where PoC validation happens, by design. The wrapper mounts `/var/run/docker.sock` and adds its group id **only when the subcommand is `validate`**; everything else about the container stays (`--cap-drop ALL`, `no-new-privileges`, no AWS access, memory/pids limits). The repo copy Strix tests is placed in the run folder on the scans volume, the one path visible to host and container alike. Documented as a deliberate exception to the container-hardening invariant. | Host install running validate as root (an agent orchestrating directly on the host, no throwaway isolation, and the foreground/nohup problem the wrapper already solved). Docker-in-Docker (unmaintained, doubles image size, nests untrusted code). |
| **OpenRouter key as a third SSM parameter** (2026-11-04) | Follows the existing token pattern (`value_wo`, read by the wrapper, never in state or on a command line). Read only for `validate`, so `scan` runs don't depend on it; the wrapper refuses to validate while it's still the placeholder. | A key baked into the image (public repo). Passing it per-invocation (the wrapper's job anyway). |
| **Strix and its sandbox pinned** (2026-11-04) | The agent is `strix-agent==1.7.0` in its own venv, like the other Python scanners, and the sandbox image tag is pinned via `STRIX_IMAGE` (`ghcr.io/usestrix/strix-sandbox:1.3.0`) and pre-pulled by `vulnscan-build`, so a validate run never pulls unpinned code and the first run doesn't wait on a multi-GB pull. | Letting Strix float to its default sandbox tag. |
| **The sandbox user is baked in as uid 10001, and Strix reaches the sandbox over the bridge** (2026-11-04) | Running Strix inside a container broke two of its assumptions. (1) On Linux, Strix passes its own uid (10001) to the sandbox, whose entrypoint remaps its `pentester` user to it, so files on the mounted target stay writable. But the entrypoint chowns `/workspace` only after a recursive chown of a 1.1 GB home directory (about 9 s), and Strix writes into `/workspace` within 0.1 s. Every run failed with `WorkspaceArchiveWriteError` (`cp: … Permission denied`). The wrapper now builds `vulnscan-strix-sandbox:1.3.0` from the pinned image with `pentester` already at uid 10001, so the entrypoint skips the remap. (2) Strix reaches the sandbox's Caido proxy at `127.0.0.1:<published port>`, which inside a container is the container itself. Caido setup then fails, and Strix carries on without its proxy tooling (usestrix/strix#1514 describes such runs exiting 0). `STRIX_DOCKER_SANDBOX_NETWORK=bridge` makes it use the sandbox's bridge IP instead and stops publishing the port on the host. Both were reproduced and verified locally with Strix's own `create_or_reuse`. | Patching Strix in site-packages to skip the remap (the agent then couldn't write the target). Running validate containers as uid 1000 (the scans volume is owned by 10001, mode 700). |
| **Dashboard: an always-on container on the instance's loopback, opened through Session Manager port forwarding** (2026-11-04) | The owner's choice. It adds no inbound rule, public address, IAM change or cost, and seeing it takes the same Session Manager access as a shell, so who can see results doesn't change. The container gets no tokens and mounts the scans read-only, with `--read-only` and the usual hardening. It's on its own Docker network so the default bridge, where Strix's sandboxes run scanned code during validation, can't reach it. It refuses non-localhost `Host` headers (DNS rebinding through the forwarded port), escapes everything, and sends a CSP that allows no scripts. `vulnscan-build` recreates it, and `--restart unless-stopped` survives Spot stops. The wrapper refuses `dashboard` because it would pass the tokens in. Tested locally with Docker Desktop: read-only mounts, uid 10001, no tokens, and unreachable from a default-bridge container. | A hosted page (ALB or S3 + CloudFront): an inbound path to a list of exploitable bugs in private code, which incident 1's hardening avoids, plus about $25 a month for an ALB and needing a login layer. A static file copied off by hand (no live view). Running it on demand from a shell (two sessions to view). `--network host` (it would reach IMDS from the host's namespace). |
| **Disks: 20 GB root, plus a separate 5 GB reports volume** (2026-11-03) | The image is about 2 GB; peak use during a rebuild is about 5 GB, plus the clone. A report is about 1 MB. A separate volume survives replacing the instance, which was verified when switching to Spot. Both can be grown without stopping the instance. | 40 GB + 20 GB (the first sizes, which were overkill). |
