# Decisions

Why vulnscan is built the way it is, including what was tried and rejected. Newest context first within each section. Dates are when the decision was made. Read the relevant entry before changing any of these things.

## Background

The project started (2026-11-03) after two incidents:
1. **An SSRF in a third-party app's URL preview leaked AWS keys.** The attacker granted themselves admin and dumped all of Parameter Store, and rotating every credential took a long time.
2. **Some systems were exploitable through a widely reported vulnerability** (HttpToShell), and the team learned about it from articles, not alerts.

The owner asked for a tool that, given any GitHub repo in their orgs, picks and installs the right scanners, finds the important vulnerabilities, stores results on the machine, and uses a Claude Code token for the LLM part.

The owner's choices:
- a proof of concept;
- only the org's own repos;
- a CLI;
- the language with the best security tooling that's easy to extend;
- a Claude Code subscription token for now.

Many of the infrastructure choices below come from incident 1: limit what a compromised scanner could reach.

## Application

| Decision | Why | Rejected |
|---|---|---|
| **Python, standard library only** (2026-11-03) | Most security tooling is Python or callable from it, and with no dependencies there's no supply-chain surface in the CLI itself. Python 3.9 is still supported for older hosts. | Go: fewer integrations and slower to extend. Third-party frameworks such as click: unnecessary. |
| **Use existing scanners and normalise their output**: semgrep, osv-scanner, gitleaks, checkov, brakeman, bandit, gosec (2026-11-03) | Each is the standard tool for its area. Together they cover code, dependencies, secrets and infrastructure for the org's stacks (Rails, JS, Python, Go, Terraform). | Writing our own rules. Commercial SaaS: code would leave the account. |
| **Never install or run the scanned repo's dependencies** (2026-11-03) | `bundle install`/`npm install` run arbitrary code from the repo. All scanners used work from source and lockfiles. | Running tests or builds, which some deeper analysers need. |
| **Claude through the headless `claude -p` CLI, restricted and read-only** (2026-11-03) | The owner chose a Claude Code subscription token. The CLI's `--restricted`, `--tools Read,Grep,Glob`, `--strict-mcp-config` and a working directory outside the repo give read-only access that can't load the repo's own settings or hooks. `--json-schema` gives structured output. | The Agent SDK or API with an API key: not the owner's choice for now. Bedrock is the planned move ([status.md](status.md)) and needs no code change. |
| **Group, prioritise and batch findings for Claude** (2026-11-04) | On a 7,700-finding monolith, the old "first 150 by severity" sent 141 dependency CVEs to Claude. CVSS rates them high, and `Gemfile.lock`/`yarn.lock` sort before `app/`. Committed private keys, SQL injection, `eval` on params and similar were all flagged by scanners but never reviewed. Now dependencies collapse per package version, noisy rules collapse to 5 samples, secrets and code come first, and up to 400 items are reviewed in batches of 100. On real data, everything on that list moved into batches 1–2. | Raising the 150 limit: one call can't take thousands of findings. Grouping brakeman: its warnings are location-specific (the SQL injection lines), so they're never grouped. |
| **Claude's own review of the code is one separate call, after the verdict batches** (2026-11-05; it was part of batch 1 from 2026-11-04) | One review per scan, as before: repeating it per batch costs time and quota and finds the same things. Inside batch 1, a review that ran past `VULNSCAN_TRIAGE_TIMEOUT` failed the whole call and lost the verdicts on the 100 most important items. On its own, it also gets the list of scanner findings Claude didn't dismiss, so it doesn't repeat them, and its summary covers every batch. Costs some re-reading of code. | Keeping it in batch 1. Once per batch. A separate deep-review mode was planned then; it was built on 2026-11-06 (the deep-review rows above). |
| **A deep review on by default, with `--no-deep-review` to skip it** (2026-11-06) | The owner's choice, after the general review missed the backend's LLM issues: the whole-codebase pass is what finds the issues no scanner sees, so it shouldn't depend on remembering a flag. It still costs hours and far more quota on a monolith, so `--no-deep-review` gives a quick scan, `--deep-path` narrows it and `--claude-budget` caps it. `--no-llm` switches it off silently. Only `--deep-review` with `--no-llm` is refused, because that asks for both. | Keeping it opt-in (the row below; the default scan would keep missing whole classes). A default `--claude-budget` (no one figure fits a small service and a monolith). |
| **An opt-in deep review, split by issue class, with coverage decided by vulnscan** (2026-11-06; on by default since, see the row above) | Claude's general review reads what it chooses in one session. A full pass per class over the whole codebase doesn't fit either: the largest local Rails app has 136k lines in 1,358 handler files, far beyond one session, so a "full" pass would quietly be a sample. So vulnscan lists what each class needs and Claude gets one batch per call. SSRF goes by sink: every outbound HTTP call site, traced back (incident 1's class, and scanners are weak at it). Access control (missing authentication or authorization, IDOR, mass assignment) goes by area: handler files grouped by folder, because those bugs live in every endpoint and no scanner sees them. The other classes are left to brakeman and semgrep, which find their sinks. Opt-in because it costs far more quota (47 calls on that app) and takes hours. `--deep-path` narrows it, and skipped or failed batches are listed so gaps are visible. Findings join Claude's own `C…` ids, so validation and fix need no change. | One whole-codebase call per class (doesn't fit, samples silently). Per area only, with every class in one checklist (SSRF sinks sit in services and jobs, away from the handlers). A pass for SQL injection, XSS and the like (re-finds what scanners find). Running calls in parallel (would hit the subscription's limits faster). |
| **Denial of service in the severity scale, and content renderers treated as SSRF sinks** (2026-11-06) | Comparing the Sonnet 5.5 and Opus 5.5 runs on scaler-hq/backend showed two gaps. First, the scale had no line for DoS, so Opus rated unauthenticated multipart DoS (starlette, python-multipart) as "limited impact" medium. Now one request, or a few, from anyone that makes the service unavailable is high, and DoS needing a login or sustained volume is medium (the owner accepted this suggestion). Second, Opus said WeasyPrint renders user-derived Markdown with its default URL fetcher, which is SSRF, yet rated it medium. The deep review's SSRF pass couldn't see that sink at all, because renderers fetch URLs inside the HTML with no HTTP call in the app's code. Renderer, headless-browser and web-loader calls are now SSRF call sites, and every prompt says such a package is rated as SSRF when users can put URLs into its content. On the largest local Rails app this added 3 WickedPdf call sites and no new batch. | Leaving DoS to "limited impact". Ignoring renderers (the SSRF behind incident 1 came through a URL feature, not a plain HTTP call). |
| **An LLM pass in the deep review, by sink** (2026-11-06) | The scaler-hq/backend deep review (2026-11-05) found the image-URL SSRF and a client-chosen model, but none of the LLM issues a separate manual review listed: candidate text steering the prompts that grade interviews, interview PII sent to providers and Langfuse, LLM output rendered as markdown. The general review's prompt asks about all of them, but its 10-issue cap went to SSRF and missing authentication, and the deep review had no LLM pass. The pass goes by sink, like SSRF. Its sites are the LLM calls plus the lines that build prompts (role messages, templates, f-string prompts), because the calls usually sit in one wrapper and untrusted text goes in where each prompt is built. On the local backend that's 212 sites in 9 batches. Order: SSRF, LLM, then access control, the biggest pass, last, so a budget cut falls there. The prompt adds a severity line, because the attacker-based scale has no place for grade manipulation or PII sent to vendors: changing a score, grade, assessment or hiring decision, or leaking solutions or rubrics, is high, and PII sent to a provider is low unless the wrong people can read it there. Moderation of what the model says stays out, because it isn't a weakness in the code. When output is rendered in another repo, such as a separate frontend, Claude says so, because only that repo shows whether it's exploitable. | Raising the general review's cap (still a sample of what Claude chooses to read). LLM calls only (the wrapper hides where untrusted text goes in). One pass per LLM risk (the same sites read several times). |
| **Every Claude call is pinned to Claude Opus 5.5 (`claude-opus-5-5`)** (2026-11-06) | The owner's choice. Without `--model`, Claude Code picks its default for the account and its own version, so the model could differ between a laptop and the instance, or change with an image rebuild. A deep review of scaler-hq/backend on the instance ran much faster and used far less quota than local runs did. Its raw output showed `claude-sonnet-5-5`, Claude Code 2.1.311's default there, while local runs on 2.1.267 had used `claude-opus-5[1m]`. `config.CLAUDE_MODEL` is passed on every call, `--model` still overrides it, and `report.json` records it. It needs Claude Code 2.1.280 or newer: the image's 2.1.311 qualifies, while a local 2.1.267 fails every call with "does not support this model". | Leaving it to Claude Code's default (opaque, varies). A `VULNSCAN_CLAUDE_MODEL` variable (not asked for; `--model` covers one-off runs). |
| **A per-scan Claude budget (`--claude-budget`)** (2026-11-06) | The owner uses a `claude setup-token` subscription token, so nothing is billed, but a scan shares the plan's allowance with the token owner's own use. A deep review of a monolith could use much of it. The cap counts `total_cost_usd` at API rates as a stand-in for quota and is checked before each call, in priority order: triage, general review, deep review. What's skipped is reported. No default cap, so normal scans behave as before. | Capping the number of calls (calls vary a lot in size). Stopping a call mid-way (loses its output). Measuring the plan's actual usage (not available to a headless run). |
| **The triage prompt: a severity scale, dependency rules, `duplicate_of`, and secrets never quoted** (2026-11-05) | From a review of the prompts. Severity decides what reaches Strix and in which order, so "re-rate by exploitability" got anchors: critical is no-login RCE, SQL injection or auth bypass, SSRF reaching cloud metadata (incident 1), or a live production credential. Unused dependencies were `confirmed` (known issue). Now never loaded → false positive, development or tests only → low, with the caveat that `Bundler.require` and transitive loading make "no import" weak evidence. A duplicate of an item in another batch, or two items marked duplicates of each other, made real issues vanish, so `duplicate` must name an item in its batch, and `_check_duplicates` keeps anything else as `needs_review`. The fix prompt forbade quoting secrets, but triage didn't: Claude reads the file gitleaks redacted, and its `reason` lands in report.md, report.csv and the dashboard. Every prompt now forbids any part of a secret's value. | A `duplicate_of` check with no schema field, parsed from the reason text. |
| **Grouped rules: samples spread across folders, and per-sample verdicts** (2026-11-05) | Samples were the first 5 files in sort order, i.e. alphabetical within a severity, so a group could be judged entirely on `spec/` or vendored hits and dismissed with its real ones. `_samples` now takes app code before tests, vendored, example and docs paths, and one per folder first. Samples carry their `F` ids, and Claude can give one its own verdict when it doesn't fit the pattern; that finding then counts as reviewed on its own. | Reviewing every hit (back to thousands of items). |
| **The scanned repo can't switch off its own findings** (2026-11-05) | An audit shouldn't let the audited code decide what's reported, and a malicious change could hide a secret or backdoor with one comment. Checked against the pinned versions: `--disable-nosem`, `--ignore-nosec` plus an empty `--ini` (replaces `.bandit`), a gitleaks config of ours plus `--ignore-gitleaks-allow` (replaces `.gitleaks.toml`), and an empty brakeman `-c` (replaces `config/brakeman.yml`). Also parsed: brakeman's `ignored_warnings`, and checkov's `skipped_checks` (needs no `--quiet`). gitleaks reads `.gitleaksignore` and checkov `.checkov.yaml` whatever the flags (tested), so those files become findings. Claude is told a suppression is the repo's claim, not proof. Costs more findings, mostly legitimate suppressions, which grouping and triage absorb. | Honouring suppressions (the default). Editing the clone to remove those files: local folders are scanned in place. `.semgrepignore` is still honoured (no flag found). |
| **A built-in prompt-injection check, plus Claude's review** (2026-11-05) | The owner asked for prompt injection in scanned repos to be checked, both kinds: text planted to steer AI tools (vulnscan's own Claude and Strix, other scanners, developers' coding agents), and injection bugs in the app's LLM features. No pinned scanner covers the first, so `tools/prompt_injection.py` is stdlib, in-process and read-only. It flags Unicode tag characters (decoded for the reader), bidi controls, zero-width runs, and phrasings that tell an AI to dismiss findings, ignore its instructions, or that address an AI by name. Triage then confirms or dismisses each, because an app's own prompts can match. Patterns were tuned on the largest local repo until it reported nothing (24 s), while still catching every planted case. Claude's review also checks agent files and agent settings that run commands (hooks, `.mcp.json`). The second kind went into the review's LLM checklist (indirect injection into agents that call tools). | An LLM pass over every file (cost on monoliths). Flagging every `CLAUDE.md` or `.cursorrules` (most are benign; Claude reads them instead). A separate category for these findings: `code` keeps the sort order and reports unchanged. |
| **Dependencies grouped by package and version, not by lockfile** (2026-11-04) | One repo had 50 lockfiles. Merging cut critical/high dependency items from 312 to 237. | Keeping the lockfile in the key. |
| **`report.csv`, with formula-injection escaping** (2026-11-04) | Requested for spreadsheets. Findings quote repo content, which is untrusted, so cells starting `=+-@` are prefixed with `'`. | — |
| **Per-org tokens (`GITHUB_TOKEN_<ORG>`) supported, but production uses one classic PAT** (2026-11-04) | A fine-grained PAT can reach only one resource owner, so two orgs need two tokens; the code supports that. The owner chose a single classic PAT with `repo` scope (plus `workflow` since 2026-11-05, see below), accepting that it also grants **write** access to every repo the user can reach. | Fine-grained per-org tokens (more secure; easy to switch back to). A GitHub App (best long-term option; needs code to mint installation tokens). |
| **Shallow clone of one branch** (2026-11-03, re-tested 2026-11-04) | Fastest and smallest. Measured on discourse/discourse (27k files): 18 s. **Rejected after testing:** a blobless clone (`--filter=blob:none`) followed by `git checkout` with exclusions fetches **one file per request** (31 requests for 28 files in 30 s), so it would take hours. A blobless clone with sparse checkout batches correctly (1 request), but was no faster on that repo, and it leaves skip-worktree entries that `git ls-files` (and so semgrep) still lists. Skipping images on the biggest repo would save about 580 MB, but clone time there is about 3.5 minutes, which is acceptable. | Full clones (history isn't scanned anyway). Mirror caching between scans: possible later for nightly runs. |
| **Per-scanner timeout of 30 minutes, adjustable per run** (2026-11-04) | One slow scanner shouldn't stall a scan forever, but large repos need longer for semgrep. `VULNSCAN_TOOL_TIMEOUT` and `VULNSCAN_TRIAGE_TIMEOUT` are passed through the wrapper. | — |
| **Validation stage uses Strix** (2026-11-04) | The owner chose agentic PoC validation for stage 2. Strix is headless-first (`strix -n` with CI exit codes), Apache-2.0, seeds findings via `--instruction-file`/`--workspace-file`, caps cost with `--max-budget`, and only reports a finding with a working proof-of-concept — exactly a validation stage. | CyberStrike: TUI/interactive-first, AGPL-3.0, thinner headless story for a pipeline. Building our own agent harness: the scanners-plus-triage approach was already ours; validation needs offensive tooling we'd otherwise write. |
| **GLM 5.3 via OpenRouter for Strix** (2026-11-04) | The owner's choice, and one of Strix's two recommended setups. GLM needs no provider safety-program enrollment (unlike OpenAI/Anthropic/Google models, which need Daybreak/CVP/Fairwind even through OpenRouter), and one OpenRouter key covers the model. `STRIX_LLM`/`LLM_API_KEY` stay standard Strix variables so any LiteLLM model id can replace it. | A Claude API key: stage 1 already uses the subscription token, and the point of stage 2 is a second, independent opinion. |
| **Validation sends each triage group once, dependencies last, and no `info`** (2026-11-05) | Claude judges a noisy rule as one item, but validation sent every hit: in a test, one 40-hit rule became 41 entries and the lone SQL injection came 41st, so a 100-hit rule would push it past `--max-validate`. A group is now one entry (its first hit outside tests and vendored code, with its hit count and other locations), and the dashboard shows its other hits as "grouped with F…". Strix rarely proves a dependency advisory, so those go last. `info` findings were never triaged but were sent. `--only` still takes any id. | Sending the whole group and relying on the cap. |
| **Strix names the ids it validates in a title tag** (2026-11-05) | `validates` came from any `F`/`C` id anywhere in Strix's text, and the instructions asked Strix to name the findings it *couldn't* validate. Strix has no channel for those, so they appeared in its reports and counted as validated ("F013 is a false positive" → F013 validated). The regex also missed `F1000` and above, which a 7,700-finding scan has. Now each title starts with `[F012, C03]` or `[new]`, only that tag counts when present, and the ids match any length. The "name what you couldn't validate" line is gone, and Strix is told to work in list order and not spend the budget on one finding. | Keeping free-text matching (over-counts). Asking Strix for a separate list of unvalidated ids (no output for it). |
| **LLM findings get their own proof criteria in Strix's instructions** (2026-11-10) | The owner asked for it. Strix's instructions only said "build a working proof-of-concept", and dropped the `found_in` label, so Strix couldn't tell a deep-review LLM finding from any other. Strix 1.7.0 ships `llm_prompt_injection` and `llm_applications` skills with sound rules (matched baseline and adversarial trials, an effect rather than the model's words), but an agent loads a skill only when it picks one, and only the `deep` scan mode's playbook mentions them, while vulnscan then ran `standard` by default (see the next row). The instructions now pass the label, name both skills, and say what counts as proof for each kind of LLM issue. They forbid testing cost or rate limits by volume, because the skill's unbounded-consumption step raises load in steps, which against a live target spends the org's LLM credits. They also forbid using provider keys found in the repo. Without `--url`, Strix is told the app's LLM calls will fail in the sandbox, so it doesn't spend a pass's budget on them. | Leaving it to Strix's own skills (an agent may never load them in `standard` mode). |
| **Strix runs in `standard` mode by default** (2026-11-11) | The owner's choice, after comparing Strix 1.7.0's playbooks. The reason `deep` was chosen, that only its playbook points agents at the LLM skills, no longer holds on its own: vulnscan's instructions name those skills in every mode (previous row). Most of what `deep` adds is exhaustive discovery (every file and endpoint, advanced techniques, a large agent swarm), while validation confirms a given list of 20. Strix estimates 30 minutes to an hour for `standard` and 1 to 4 hours for `deep`, against the 2-hour `VULNSCAN_VALIDATE_TIMEOUT`. `--scan-mode deep` still works for one run. Not yet compared on a real run. | Keeping `deep` (the next row). |
| **Strix runs in `deep` mode by default** (2026-11-10; replaced 2026-11-11 by the previous row) | The owner's choice. `deep` is also Strix's own default, and its playbook is the only one that points agents at the LLM skills. It costs time and budget: a pass can take hours and is more likely to spend its whole `--budget`, and a pass that runs past `VULNSCAN_VALIDATE_TIMEOUT` (default 2 hours) counts as failed. `--scan-mode quick` or `standard` still works for one run. Checked on 2026-11-10: Strix 1.7.0 is still the latest release on PyPI and GitHub, and its default sandbox is the pinned 1.3.0. | Keeping `standard` (vulnscan's default until then). |
| **Every validate and fix run starts from scratch** (2026-11-11) | The owner's choice: a re-run shouldn't skip what an earlier run covered. Validate used to carry on with the findings no pass had been sent. That meant a finding in a pass that ran out of budget counted as sent even if Strix never reached it. Fix used to skip any finding whose branch existed. Now a validate run without `--only` sends every open critical and high finding again. It replaces the earlier results, which the owner chose over keeping both (keeping both would list the same issue twice). It also removes the fix results, which name findings by the old `V…` ids. `--only` still adds, because it validates chosen findings rather than everything. A failed pass no longer stops the run: a re-run starts over anyway, so stopping would only leave the later passes untried. Fix calls Claude for every finding on every run. | Carrying on from where the last run stopped (what this replaces). Keeping each validation's results side by side (more files, and the dashboard would have to pick one). |
| **Fix branches are named after the stage-1 findings, and a re-run updates the PR** (2026-11-11) | The owner chose updating the existing PR over opening a new PR each run or closing the old one. Branches were named after `V…` ids, which start again at `V001` on every full validation, so they'd point at different findings. The stage-1 ids a finding validates (`F012`, `C03-F012`) don't change within a scan. So a re-run, even after a re-validation, finds the same branch, force-pushes the new fix, and updates the open PR's title, body and base. The costs: commits people pushed to a `vulnscan/fix-*` branch are lost, and a finding that validates a different set of ids next time gets a new branch. A `[new]` finding has no stage-1 id, so its key is a hash of its title and location, and it matches only if Strix words it the same way. When findings share a key, the first in `V…` order keeps it and the later ones get their `V…` id added, so validating a finding again with `--only` doesn't move its branch. After a re-validation, though, which of them comes first can change, and then the other one's fix is force-pushed to that branch and its PR or issue is rewritten for it. That's accepted, because the branch belongs to the stage-1 finding, and both validated findings are that finding. The fix-branch check in `validate` (rows below) was removed: branch names no longer depend on `V…` ids. Branches from before this change are named after `V…` ids and aren't matched. A branch that already existed is never deleted after a failed PR update, because that would close its PR. | A new PR every run (duplicates pile up). Closing the old PR and opening a new one (loses the review history). Matching by `V…` id (renumbered by every validation). |
| **`vulnscan purge scan\|validate\|fix`** (2026-11-11) | The owner asked for a command to purge each stage's results. A stage's results go together with the later stages', which depend on them: fix results name the validation's `V…` ids, and a scan's run folder holds all three. The owner chose the defaults: the repo's newest run with those results (`--run` or `--all` for others), and local files only, never PRs or branches. Without `--yes` it only lists, because on the instance it runs in a detached container that can't ask for confirmation. `--run` must name a folder directly under the repo's scans folder, so it can't delete anything else. | Closing PRs and deleting branches as well (it acts on GitHub). Every run by default. |
| **Progress is logged as it happens** (2026-11-11) | The owner saw long stretches with no output. A Claude call printed nothing until it ended, up to an hour later, and a Strix pass stayed silent for hours. Claude now runs with `--output-format stream-json --verbose`, and its events are read as they arrive. Each tool call is logged with its file or folder, and the final `result` event, the same JSON as before, is saved and read. Grep patterns aren't logged, since one could quote a secret's value, and tool results (file contents) are neither logged nor kept. Strix's headless output is a status panel that renders only on a terminal, plus a panel per finding. So vulnscan tails the `strix.log` that Strix writes into its run folder, and relays agent starts and ends, vulnerability reports and errors. Scanners get a "still running" line every minute, and every line gets the time. The stream format was checked with a real Claude Code 2.1.267 call, and the log format against Strix 1.7.0's source. | Relaying Strix's stdout (nothing useful in headless mode). Logging Claude's text and tool results (could quote secrets). |
| **Findings Claude can't fix get a GitHub issue** (2026-11-11) | The owner's choice. A validated finding with no safe automated fix used to end as `not fixed` in `fix.md`, which nobody outside the instance sees. Now it gets an issue in the repo with what's wrong, the steps to reproduce, and why there's no automated fix, which Claude is asked to explain as what a person must decide or do. A new `still_present` field separates that from "already gone from this code", which gets no issue. Like PRs, issues never go to public repos (`fix` refuses them without `--dry-run`, and a dry run opens none), and they never carry Strix's raw PoC. A re-run updates the issue instead of opening another. It's matched by a marker in its body, keyed like the branch, among the open issues the token's user created. That lookup calls `GET /user`, so it needs a user's token. A finding whose earlier PR is still open gets no issue, since the PR tracks it. vulnscan doesn't close issues: a later run that fixes the finding opens a PR, and a person closes the issue. A repo with issues turned off (HTTP 410) isn't a failure. | Jira or Linear (the owner asked for an issue in the repo). Finding earlier issues through the search API (rate-limited, and slow to see new issues). Closing the issue when a later run opens a PR (the PR isn't merged yet). |
| **`vulnscan validate` as a separate stage reading stage-1's `report.json`** (2026-11-04) | Stages stay explicit and separately runnable (and re-runnable against the same run folder), the expensive validation is opt-in, and the stage-1 report is a natural handoff: its open findings — confirmed, needs review, not triaged, plus Claude's own — are the validation worklist. `--max-validate` capped it, mirroring `--max-triage` (replaced 2026-11-06 by passes of 20 critical and high findings). | Folding validation into `vulnscan scan --validate`: couples two expensive stages and forces the clone to be kept. |
| **vulnscan clones, Strix gets a local directory; the GitHub token never reaches Strix** (2026-11-04) | Strix can take a GitHub URL itself, but that would mean handing it the token (in its environment or its sandbox). Cloning ourselves reuses stage-1's token handling and org allowlist. Strix mounts local targets **writable**, so local folders are copied to a throwaway directory first; our clones are already throwaway. | Passing the repo URL plus `GITHUB_TOKEN`. Pointing Strix at a permanent local checkout (it edits what it mounts). |
| **Strix's Docker sandbox is the boundary where scanned code runs** (2026-11-04) | Stage 2's whole purpose is to run and probe the app, which stage 1 forbids for scanners. Strix's sandbox (`ghcr.io/usestrix/strix-sandbox`, pinned by them) is the isolation boundary; it never runs in the vulnscan container. Only `--url` targets extend reach beyond it, and those are the operator's authorisation to give. | Relaxing the stage-1 invariant inside the vulnscan container. |
| **`vulnscan fix`: one draft PR per Strix-validated finding** (2026-11-04) | The owner's choices. Only `V…` findings are fixed, because they have a working PoC. Stage-1 "confirmed" findings don't. One PR per finding keeps each change small and separately mergeable or revertable. PRs are drafts because Claude can't run the repo's code or tests; that would break the "never run scanned code" invariant. | Fixing stage-1 confirmed critical/high findings too. One PR with all fixes, which is harder to review and merge piece by piece. Ready-for-review PRs. |
| **Fix stage: Claude gets Edit/Write, and vulnscan does the git and GitHub work** (2026-11-04) | The owner's choice, and the one exception to "Claude is read-only". Claude stays `--restricted`, with no shell, web or MCP and no GitHub token. Verified: `--restricted` with `acceptEdits` edits files in `--add-dir` headlessly, but refuses writes to `.git/hooks`. The token stays in vulnscan, which commits, pushes (`GIT_CONFIG_*`) and calls the API.
